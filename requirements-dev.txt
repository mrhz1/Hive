# Pinned for Python 3.10 -- impyla's thrift-sasl/sasl chain is fragile on
# newer Pythons (3.12+/3.14 fail to build the `sasl`/`pure-sasl` C extension
# and impyla's transport negotiation breaks). Use the 3.10.20 pyenv
# interpreter for this venv: `~/.pyenv/versions/3.10.20/bin/python3 -m venv .venv`
#
# impyla/thrift 0.24.0 specifically: on impyla 0.20.0 (which hard-pins
# thrift==0.16.0) the thrift C accelerator `fastbinary` raises
#   SystemError: PY_SSIZE_T_CLEAN macro must be defined for '#' formats
# when decoding a FetchResults response, so any query returning more than
# a handful of rows 500s. Reproduced on thrift 0.16.0 AND 0.21.0; fixed on
# 0.24.0. Do not downgrade impyla below 0.24.0 without re-testing a
# multi-row fetch (scripts/check_hive.py alone will NOT catch it -- SHOW
# DATABASES is small enough to pass either way).
impyla==0.24.0
thrift==0.24.0
thrift-sasl==0.4.3
fastapi==0.111.0
# Required by FastAPI to parse multipart/form-data (patient file uploads).
python-multipart==0.0.32
uvicorn==0.30.1
structlog==24.4.0
pytest==8.2.2
# Runtime, not just test: app/cloudera.py posts to the Cloudera AI API v2

# (FastAPI's TestClient also needs it.)
httpx==0.27.0
# Serves frontend/dist as a Cloudera AI Application -- a React build is
# not deployable on its own there, something has to run as a process.

flask==3.0.3
python-dotenv==1.0.1

# Document metadata extraction (app/file_metadata.py), read once per
# upload and stored in `file_metadata`. All three are pure Python with no
# system libraries, which is what keeps them acceptable in the API
# process -- the heavy OCR/ML stack deliberately stays in the Job.
#
# Note this is metadata only: none of these renders or OCRs anything, so
# they do not overlap with the OCR venvs.
pypdf==5.1.0
pydicom==3.0.1
python-docx==1.1.2
# python-docx reads only the 2007+ zip format. A pre-2007 .doc is an OLE2
# compound file, and .doc is an accepted upload, so without this every
# legacy Word document records 'failed' with no metadata at all. olefile
# is pure python with no dependencies of its own; if it is ever missing,
# extraction degrades back to that same 'failed' row rather than erroring.
olefile==0.47

# Rendering for the viewer (app/preview.py): a browser downloads a DICOM
# and a Word document rather than displaying them, so the API turns a
# DICOM frame into a PNG and a .docx into text.
#
# pydicom decodes only uncompressed and RLE pixel data by itself, and
# most PACS studies are compressed -- these are the same decoders the
# OCR job needs, for the same reason. See OCR/requirements-ocr.txt.
#
# This is still not the ML stack: numpy and pillow are array and image
# plumbing, not inference, and nothing here OCRs anything.
numpy>=1.24,<2.4
pillow>=10.0.0
pylibjpeg>=2.0
pylibjpeg-libjpeg>=2.1     # JPEG, JPEG Lossless, JPEG-LS
pylibjpeg-openjpeg>=2.2    # JPEG 2000, HTJ2K

# Stamps the patient id onto de-identified PDFs when an application is
# submitted (app/stamp.py).
#
# This file used to say pypdf was chosen *over* pymupdf because the API
# "would only use it to read a document info dictionary". That was true
# while the API only read PDFs. Stamping writes one, and drawing text
# with pypdf means hand-building an overlay page with its own font
# resource -- fiddly, easy to get subtly wrong, and still not a real
# content-stream stamp. A 20MB binary wheel is the cheaper answer.
#
# It is still not the ML stack: pymupdf renders and edits PDFs, and the
# OCR/NER dependencies stay in the Job. Both OCR venvs already carry it.
pymupdf==1.24.14

# Writes the metadata export (app/routers/patient_application_files.py).

# and dates, and Excel silently reformats both when it guesses at a CSV
# -- a 16-digit serial comes back as 1.78633E+15.
openpyxl==3.1.5
